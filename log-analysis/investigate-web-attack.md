# Кейс: Investigate Web Attack — разведка и веб-атака по access-логу

**Категория:** Log Analysis / Web Attack Detection
**Платформа:** [LetsDefend — Investigate Web Attack](https://app.letsdefend.io/challenge/investigate-web-attack)
**Инструменты:** ручной разбор access-лога (Apache/nginx combined log), сигнатуры сканеров, regex

## Обзор

Расследование по сырому access-логу веб-сервера, обслуживающего уязвимое учебное приложение **bWAPP** (`/bWAPP/`). Задача — восстановить хронологию атаки: с чего начал злоумышленник, какими инструментами пользовался, что именно эксплуатировал.

## Окружение

- Целевой хост в логе: `192.168.199.5` (bWAPP)
- IP из лога, связанные с активностью: `192.168.199.1`, `192.168.199.2`
- Формат лога: Apache/nginx combined (`IP - - [время] "METHOD path HTTP/ver" статус размер "referer" "user-agent"`)

## Шаг 1. Инструмент автоматической веб-разведки

**Вопрос:** Какой инструмент автоматического сканирования использовал злоумышленник для веб-разведки?

Фрагмент лога, где начинается активность второго IP (`192.168.199.2`):

```
192.168.199.2 - - [20/Jun/2021:12:36:24 +0300] "HEAD / HTTP/1.1" 200 - "-" "Mozilla/5.00 (Nikto/2.1.6) (Evasions:None) (Test:Port Check)"
192.168.199.2 - - [20/Jun/2021:12:36:24 +0300] "GET /bwapp/ HTTP/1.1" 302 "-" "Mozilla/5.00 (Nikto/2.1.6) (Evasions:None) (Test:getinfo)"
192.168.199.2 - - [20/Jun/2021:12:36:24 +0300] "GET /bwapp/ HTTP/1.1" 302 "-" "Mozilla/5.00 (Nikto/2.1.6) (Evasions:None) (Test:map_codes)"
192.168.199.2 - - [20/Jun/2021:12:36:24 +0300] "GET /bwapp/4RaXX5Ac.exe HTTP/1.1" 404 300 "-" "Mozilla/5.00 (Nikto/2.1.6) (Evasions:None) (Test:map_codes)"
192.168.199.2 - - [20/Jun/2021:12:36:24 +0300] "GET /bwapp/4RaXX5Ac.show HTTP/1.1" 404 300 "-" "Mozilla/5.00 (Nikto/2.1.6) (Evasions:None) (Test:map_codes)"
...
```

**Ответ: Nikto** (версия 2.1.6).

Признаки, по которым это определяется однозначно, а не предположительно:

1. **User-Agent прямо называет инструмент** — `Mozilla/5.00 (Nikto/2.1.6) (Evasions:None) (Test:...)`. Это не подделанный UA под браузер — Nikto по умолчанию честно представляется, если не включена маскировка.
2. **Формат UA специфичен для Nikto** — сегменты `(Evasions:...)` и `(Test:...)` не общая практика, а особенность конкретно Nikto: он вписывает в свой же User-Agent название текущей выполняемой проверки (`Port Check`, `getinfo`, `map_codes`) и статус техник обхода детекта (evasions). Инструмент вроде dirb/gobuster так не делает.
3. **`Test:map_codes` со случайным именем файла** (`4RaXX5Ac.exe`, `4RaXX5Ac.show`, `4RaXX5Ac.java`...) — это узнаваемая техника самого Nikto: он запрашивает заведомо несуществующий путь со случайным именем и разными расширениями, чтобы понять, как сервер обрабатывает 404 (нет ли кастомной страницы ошибки, которая маскирует реальные результаты сканирования под "не найдено").
4. **Темп запросов** — множество запросов в одну и ту же секунду (`12:36:24`) с одного IP — не то, как ведёт себя человек в браузере, характерно для автоматизированного инструмента.

## Шаг 2. Метод обнаружения содержимого каталогов

**Вопрос:** После проведения веб-разведки, какой метод использовал злоумышленник для обнаружения содержимого каталогов?

Фрагмент лога — тот же IP (`192.168.199.2`), уже после сканирования Nikto:

```
192.168.199.2 - - [20/Jun/2021:12:38:02 +0300] "GET /bwapp/admin/2004 HTTP/1.1" 404 300 "-" "Mozilla/4.0 (compatible; MSIE 6.0; Windows NT 5.1)"
192.168.199.2 - - [20/Jun/2021:12:38:02 +0300] "GET /bwapp/admin/2005 HTTP/1.1" 404 300 "-" "Mozilla/4.0 (compatible; MSIE 6.0; Windows NT 5.1)"
...
192.168.199.2 - - [20/Jun/2021:12:38:02 +0300] "GET /bwapp/admin/2014 HTTP/1.1" 404 300 "-" "Mozilla/4.0 (compatible; MSIE 6.0; Windows NT 5.1)"
192.168.199.2 - - [20/Jun/2021:12:38:02 +0300] "GET /bwapp/admin/21 HTTP/1.1" 404 300 "-" "Mozilla/4.0 (compatible; MSIE 6.0; Windows NT 5.1)"
```

**Ответ: Directory/Content Brute-Forcing (Forced Browsing)** — перебор каталогов по словарю/списку значений в поисках существующих, но не проиндексированных путей.

Уточнение по коду ответа: в логе **404 Not Found**, не 400 — 400 означало бы, что сам запрос синтаксически некорректен (проблема на стороне клиента в формировании запроса), тогда как 404 означает "запрос корректен, но такого ресурса на сервере нет". Именно 404 и подтверждает вывод: перебираемые пути `/bwapp/admin/2004`...`/bwapp/admin/2014`, `/bwapp/admin/21` — не существуют, атакующий просто перебирает кандидатов.

Дополнительные наблюдения по этому фрагменту:

- **User-Agent сменился** — теперь `Mozilla/4.0 (compatible; MSIE 6.0; Windows NT 5.1)`, вместо явного `Nikto/2.1.6` из Шага 1. Это либо сам Nikto с изменённым/дефолтным UA для отдельного модуля брутфорса, либо отдельный инструмент directory-брутфорса (например Dirbuster/wfuzz с кастомным UA), запущенный тем же атакующим с того же IP. Явной сигнатуры инструмента в самом UA здесь уже нет — только по паттерну запросов (перебор коротких числовых путей под `/bwapp/admin/`) видно, что это автоматизированный брутфорс, а не Nikto-специфичный скан.
- Все запросы в один и тот же timestamp (`12:38:02`) — снова темп, невозможный для ручного перебора человеком.

## Шаг 3. Третий тип атаки — после обнаружения каталога через листинг

**Вопрос:** Какой третий тип атаки следует за обнаружением путём просмотра списка файлов в каталоге?

Фрагмент лога — атакующий (`192.168.199.2`) сначала подгружает статику страницы логина bWAPP (браузерная сессия, обычные GET на `/BWAPP/images/...`, `stylesheet.css`, шрифт), затем:

```
192.168.199.2 - - [20/Jun/2021:12:41:41 +0300] "POST /BWAPP/login.php HTTP/1.1" 200 4086 "http://192.168.199.5/BWAPP/login.php" "Mozilla/5.0 (X11; Linux x86_64; rv:52.0) Gecko/20100101 Firefox/52.0"
192.168.199.2 - - [20/Jun/2021:12:42:23 +0300] "POST /BWAPP/login.php HTTP/1.1" 200 4086 "http://192.168.199.5/BWAPP/login.php" "Mozilla/5.0 (X11; Linux x86_64; rv:52.0) Gecko/20100101 Firefox/52.0"
```

**Ответ: Brute Force атака на форму авторизации** (`/BWAPP/login.php`) — третий этап после разведки (Nikto) и обнаружения каталогов (directory brute-force): атакующий переходит от "найти, что есть на сервере" к "подобрать валидные учётные данные".

**Почему это распознаётся как брутфорс, а не единичная попытка входа:**
- Множественные `POST` на один и тот же `/BWAPP/login.php` с одного IP подряд.
- Referer указывает на саму страницу логина — типично для формы, которая пересылает сама себя при неверном пароле.

**Почему атака не удалась (несмотря на код 200):**
- bWAPP, как и многие уязвимые учебные/реальные приложения, возвращает **200 OK даже при неверном логине** — ошибка показывается на той же странице, а не через `401 Unauthorized`. Поэтому код ответа здесь бесполезен для различения успеха/провала.
- Рабочий признак — **размер тела ответа** (`4086` байт в обоих случаях): при неудачном логине сервер каждый раз отдаёт одну и ту же страницу с формой + сообщением об ошибке → размер стабилен. Успешный логин почти всегда даёт другой размер (другая разметка дашборда/портала) или редирект (`302`) вместо `200`.

> ⚠️ **На что обратить внимание при таком выводе:** двух одинаковых по размеру ответов подряд — начало доказательства, не финальное. Для уверенного вывода "брутфорс провалился полностью" нужно пройтись по ВСЕМ POST-запросам к `login.php` в логе и убедиться, что размер ответа не меняется вообще нигде вплоть до конца сессии — если хоть один ответ отличается по размеру (или это `302`, или появляется `Set-Cookie` с сессионным токеном) — это может быть момент успешного входа, который легко пропустить, если остановиться на первых двух строках.

## Шаг 4. Итог брутфорса — успех или провал?

**Вопрос:** Удастся ли третья атака (брутфорс формы логина)?

Продолжение серии POST-запросов к `/BWAPP/login.php`, вплоть до перелома:

```
192.168.199.2 - - [20/Jun/2021:12:47:49 +0300] "POST /BWAPP/login.php HTTP/1.1" 200 4086 "http://192.168.199.5/BWAPP/login.php" "..."
192.168.199.2 - - [20/Jun/2021:12:47:50 +0300] "POST /BWAPP/login.php HTTP/1.1" 200 4086 "http://192.168.199.5/BWAPP/login.php" "..."
192.168.199.2 - - [20/Jun/2021:12:47:52 +0300] "POST /BWAPP/login.php HTTP/1.1" 200 4086 "http://192.168.199.5/BWAPP/login.php" "..."
192.168.199.2 - - [20/Jun/2021:12:49:35 +0300] "POST /BWAPP/login.php HTTP/1.1" 200 4086 "http://192.168.199.5/BWAPP/login.php" "..."
192.168.199.2 - - [20/Jun/2021:12:49:35 +0300] "POST /BWAPP/login.php HTTP/1.1" 302 -    "http://192.168.199.5/BWAPP/login.php" "..."   ← перелом
192.168.199.2 - - [20/Jun/2021:12:50:10 +0300] "POST /BWAPP/portal.php HTTP/1.1" 302 23369 "http://192.168.199.5/BWAPP/login.php" "..."
192.168.199.2 - - [20/Jun/2021:12:50:10 +0300] "GET  /BWAPP/portal.php HTTP/1.1" 200 23369 "http://192.168.199.5/BWAPP/login.php" "..."
```

**Ответ: Да, брутфорс в итоге успешен.**

Разбор перелома:

1. До `12:49:35` — стабильно `200`, `4086` байт: та же страница логина с ошибкой, попытка за попыткой.
2. На `12:49:35` — тот же POST, но теперь **`302`** (редирект) вместо `200`. Смена кода статуса на редирект после POST на форму логина — практически универсальный признак успешной аутентификации (классический паттерн **POST/Redirect/GET**: сервер обрабатывает форму, затем перенаправляет на защищённую страницу вместо повторного рендера формы).
3. Дальше браузер атакующего следует за редиректом на `portal.php` и получает **`200`, `23369` байт** — на порядок больше, чем `4086` у страницы логина: это уже реальный контент личного кабинета/портала, а не форма с ошибкой.

Совпадение сразу трёх независимых признаков (смена кода на 302 → редирект именно на `portal.php` → резкий скачок размера ответа) не оставляет места для альтернативной интерпретации — это подтверждённый успешный вход.

## Шаг 5. Четвёртая атака — Code Injection

**Вопрос:** Как называется четвёртая атака?

После успешного входа атакующий переходит на `phpi.php` (говорящее имя — **PHP Injection**, одна из специально уязвимых страниц bWAPP) и сначала пробует безобидное значение параметра:

```
192.168.199.2 - - [20/Jun/2021:12:50:17 +0300] "GET /bWAPP/phpi.php?message=test HTTP/1.1" 200 12759 "http://192.168.199.5/bWAPP/phpi.php" "..."
192.168.199.2 - - [20/Jun/2021:12:51:37 +0300] "GET /bWAPP/phpi.php?message=test HTTP/1.1" 200 12759 "..." "..."
```

Затем — payload'ы с явным разрывом контекста и вызовом `system()`:

```
GET /bWAPP/phpi.php?message=%22;%20system(%27whoami%27) HTTP/1.1" 200 12778
GET /bWAPP/phpi.php?message=%22;%20system(%27net%20user%27) HTTP/1.1" 200 13045
GET /bWAPP/phpi.php?message=%22;%20system(%27net%20share%27) HTTP/1.1" 200 13175
GET /bWAPP/phpi.php?message=%22;%20system(%27net%20user%20hacker%20Asd123!!%20/add%27) HTTP/1.1" 200 12755
```

**Ответ: Code Injection** (конкретно — PHP Code Injection, эскалирующий до OS Command Injection через `system()`).

**Разбор payload'а** (декодируя `%22` → `"`, `%20` → пробел, `%27` → `'`):

```php
"; system('whoami')
```

Классический разрыв контекста: закрывающая кавычка `"` завершает исходную строку, в которую подставлялся параметр `message` (например внутри `eval()` или конкатенации в исполняемый PHP-код), точка с запятой `;` начинает новый оператор, а `system(...)` — уже прямой вызов функции ОС из PHP.

**Прогрессия команд атакующего — учебниковый пример post-exploitation recon → persistence:**

| Payload | Что делает | Зачем атакующему |
|---|---|---|
| `whoami` | Кто я на сервере | Проверка контекста выполнения (какие права) |
| `net user` | Список локальных пользователей | Разведка (Discovery) |
| `net share` | Список сетевых шар | Разведка возможностей для дальнейшего движения |
| `net user hacker Asd123!! /add` | **Создаёт нового локального пользователя** `hacker` с паролем `Asd123!!` | **Persistence** — бэкдор-аккаунт, не зависящий от исходной уязвимости |

**MITRE ATT&CK:**
- `T1190` — Exploit Public-Facing Application (эксплуатация `phpi.php`)
- `T1059` — Command and Scripting Interpreter (выполнение команд через `system()`)
- `T1136.001` — Create Account: Local Account (создание `hacker`)

> 🚨 **Критично для реагирования:** последний payload — не разведка, а закрепление в системе. Даже если исходную уязвимость `phpi.php` закрыть, аккаунт `hacker` останется в системе и даст доступ снова. Первоочередное действие при таком выводе — не просто пропатчить код, а **удалить/заблокировать созданный аккаунт** и проверить, не менялись ли группы/права (не добавлен ли `hacker` в локальных администраторов).

## Шаг 6. Признаки закрепления (persistence) в системе

**Вопрос:** Есть ли в лог-файле признаки сохранения активности на целевом компьютере? Если да, то какая полезная нагрузка к этому относится?

**Ответ: Да, есть.** Payload из строки `12556`:

```
GET /bWAPP/phpi.php?message=%22;%20system(%27net%20user%20hacker%20Asd123!!%20/add%27) HTTP/1.1
```

Уже разобран в [Шаге 5](#шаг-5-четвёртая-атака--code-injection) — после decode это `"; system('net user hacker Asd123!! /add')`, команда создания локального пользователя `hacker` с паролем `Asd123!!`. Это и есть persistence: доступ, который переживёт исправление исходной уязвимости в `phpi.php`.

**Важная поправка по терминологии декодирования:** `%22`, `%27`, `%20` — это **URL-кодирование (percent-encoding, RFC 3986)**, не Base64.

| | URL-encoding | Base64 |
|---|---|---|
| Вид | `%XX` — каждый спецсимвол как процент + 2 hex-цифры его ASCII/UTF-8 кода | Сплошная строка из алфавита `A-Za-z0-9+/=`, длина кратна 4 (с паддингом `=`) |
| Пример | `%27` = `'` (ASCII `0x27`) | `bmV0IHVzZXI=` = `net user` |
| Где типично встречается | Query string / form-data веб-запросов | `-EncodedCommand` в PowerShell, вложения, обфускация payload'ов в теле |
| Как декодировать | `urllib.parse.unquote()`, `python3 -c "import urllib.parse; print(urllib.parse.unquote('...'))"`, или просто вручную по таблице ASCII | `base64 -d`, `echo '...' \| base64 -d` |

Путать их легко (оба выглядят как "непонятная строка вместо текста"), но метод декодирования — разный, и если применить не тот (например попытаться `base64 -d` к URL-encoded строке) — на выходе будет мусор, а не читаемая команда.

## Выводы (промежуточные)

- User-Agent — первое, что стоит проверять при подозрении на автоматическое сканирование, но важно уметь отличить "просто упомянутое имя инструмента" от **структурных** признаков конкретно этого инструмента (для Nikto — формат `(Evasions:X) (Test:Y)`), чтобы не полагаться только на строку, которую легко подделать.
- `Test:map_codes` со случайным именем файла — полезная сигнатура для детект-правила: запрос на несуществующий путь со случайной алфавитно-цифровой строкой в имени и множеством разных расширений подряд с одного IP.
- Directory/content brute-forcing различим по паттерну путей (короткие предсказуемые сегменты — числа, общие словарные слова типа `admin`) и коду **404** на большинство запросов при единичных "попаданиях" — а не по User-Agent, который атакующий может как угодно менять между этапами атаки.
- Важно не путать коды 4xx между собой в отчётах: 400 (Bad Request) ≠ 404 (Not Found) ≠ 403 (Forbidden) — каждый говорит о разной причине отказа и по-разному читается при триаже.
- Когда приложение возвращает `200 OK` и на успех, и на провал (частый анти-паттерн в вебе, в т.ч. в bWAPP) — единственный надёжный признак результата login-брутфорса в access-логе — **размер тела ответа**, а не код статуса. Проверять нужно ВСЕ POST-запросы к форме логина, а не первые несколько — успешный вход может затеряться посреди сотен неудачных.
- Паттерн **POST → 302 → GET защищённой страницы → 200 с другим (обычно большим) размером** — надёжная сигнатура успешного логина в access-логе практически для любого веб-приложения, использующего Post/Redirect/Get, не только для bWAPP.
- Прогрессия payload'ов в Code/Command Injection обычно предсказуема: сначала безобидная разведка (`whoami`, `net user`), затем — persistence (создание аккаунта/задачи/службы). Если в логе видна разведка через command injection, стоит сразу целенаправленно искать команды создания пользователей/задач сразу следом, а не считать инцидент закрытым на этапе "просто выполнили whoami".
- URL-encoding (`%XX`) и Base64 — разные кодировки с разным декодированием, легко перепутать на вид. В query string веб-запроса почти всегда URL-encoding; Base64 чаще встречается в теле payload'ов (например `-EncodedCommand` в PowerShell).
